# Отчёт о статическом анализе (SAST)

## Область проверки

Я проверил исходный код учебного сервиса собственными правилами Semgrep,
зависимости контейнерного образа — Trivy, а Dockerfile — проверками
конфигурации Trivy. Проверка зависимостей относится к SCA, но её результаты
я включил в этот отчёт вместе со статическим анализом кода и конфигурации.

Учебные SQL Injection и BOLA/IDOR предусмотрены заданием. Я оставил их в
коде, а обнаруженные проблемы зависимостей и Dockerfile рассмотрел отдельно.

## Правила для исходного кода

Я описал два правила в файле [test_ruels.yml](test_ruels.yml).
Оба используют режим `taint`, чтобы отслеживать путь данных от входного
параметра до вызова SQL-запроса.

| Правило | Уровень | Что проверяет |
| --- | --- | --- |
| `lab-search-sql-injection` | ERROR | Попадание параметра `q` из `search_notes` в текст SQL, передаваемый в `execute` |
| `lab-lab-bola` | WARNING | Попадание параметра `id` из `get_note` в параметры `execute`; сигнал для проверки прав доступа |

В `search_notes` пользовательский `q` вставляется в SQL через f-строку.
Вызов `lab_sanitize(q)` не защищает запрос: функция возвращает строку
без изменений. Это соответствует намеренной SQL-инъекции.

В `get_note` запрос параметризован, но выбирает заметку только по `id`.
Пользователь проходит аутентификацию, однако принадлежность заметки его
`user_id` не проверяется. Это намеренная BOLA/IDOR.

Правило WARNING указывает место для проверки авторизации: само попадание
`id` в параметры SQL ещё не доказывает BOLA. Я подтвердил отсутствие
проверки владельца при просмотре кода и ручном тестировании стенда.
Отдельного сохранённого вывода запуска Semgrep в проекте нет, поэтому
количество автоматических сработок здесь не фиксирую.

## Проверка зависимостей

### Первичная проверка Starlette

Первичная проверка выполнялась при следующих прямых зависимостях:

```text
fastapi==0.115.12
uvicorn==0.34.2
psycopg[binary]==3.2.6
```

В первоначальных результатах для установленной Starlette `0.46.2`
были перечислены следующие находки. Оценку применимости я сделал по
используемым маршрутам и компонентам сервиса.

| CVE | Уровень | Исправленная версия по первичному отчёту | Оценка для стенда |
| --- | --- | --- | --- |
| CVE-2025-62727 | HIGH | 0.49.1 | `FileResponse` и `StaticFiles` не используются |
| CVE-2026-48818 | HIGH | 1.1.0 | Стенд работает в Linux; `StaticFiles` не используется |
| CVE-2026-54283 | HIGH | 1.3.1 | Обработчики принимают JSON; вызовов `request.form()` нет |
| CVE-2025-54121 | MEDIUM | 0.47.2 | Разбор multipart и загрузка через `UploadFile`/`File` отсутствуют |
| CVE-2026-48710 | MEDIUM | 1.0.1 | Требовала проверки использования `request.url` и Host в ограничениях доступа |
| CVE-2026-48817 | MEDIUM | 1.1.0 | Используются обычные маршруты FastAPI; подклассов `HTTPEndpoint` нет |
| CVE-2026-54282 | LOW | 1.3.0 | Требовала проверки обработки пути и использования `request.url.hostname/netloc` |

Эта оценка описывает доступность затронутых компонентов в стенде;
она не означает, что старая версия библиотеки лишена уязвимостей.

### Обновление и повторное сканирование

Я попробовал установить Starlette `1.3.0` вместе с FastAPI `0.115.12`,
но получил конфликт: эта версия FastAPI требует
`starlette>=0.40.0,<0.47.0`.

После этого я обновил зависимости и пересобрал образ. В текущем
[requirements.txt](requirements.txt) указано:

```text
fastapi==0.134.0
uvicorn==0.34.2
psycopg[binary]==3.2.6
starlette==1.3.1
```

Сохранённый результат проверки образа — [trivy-report.txt](trivy-report.txt).
В нём для Starlette `1.3.1`, FastAPI `0.134.0`, Uvicorn `0.34.2`,
psycopg `3.2.6` и остальных перечисленных Python-пакетов, кроме pip,
указано **0 находок**.

При этом образ целиком не получил нулевой результат:

| Компонент | Находок | Распределение по уровню риска |
| --- | --- | --- |
| Пакеты Debian 13.7 | 201 | UNKNOWN: 4, LOW: 65, MEDIUM: 82, HIGH: 50, CRITICAL: 0 |
| pip 25.0.1 | 6 | Подробности приведены в исходном отчёте |
| Starlette 1.3.1 | 0 | — |

Таким образом, обновление устранило находки по Starlette в сохранённом
повторном отчёте. Находки базового образа и pip остаются отдельным
результатом проверки; их исправление в этом этапе не зафиксировано.

## Проверка Dockerfile

При первичном сканировании Dockerfile Trivy выполнил 27 проверок:
25 прошли, две завершились с ошибкой.

| Проверка | Уровень | Причина | Внесённое исправление |
| --- | --- | --- | --- |
| DS-0002 | HIGH | Не задан непривилегированный пользователь | Созданы группа и пользователь `app` с GID/UID `10001`, добавлена инструкция `USER app` |
| DS-0026 | LOW | Отсутствует `HEALTHCHECK` | Добавлена HTTP-проверка существующего `/openapi.json` |

Пользователь `app` создан без домашнего каталога, с оболочкой
`/usr/sbin/nologin`. Приложение запускается от его имени.

Проверка здоровья использует стандартную библиотеку Python
`urllib.request` и обращается к `http://127.0.0.1:8000/openapi.json`.
Интервал — 30 секунд, HTTP-таймаут — 2 секунды, таймаут Docker — 3 секунды,
стартовый период — 20 секунд. Три последовательные неудачи переводят
контейнер в состояние `unhealthy`. Дополнительный endpoint не создавался.

После пересборки я повторил проверку:

```bash
trivy config Dockerfile
```

В сохранённой здесь сводке повторного сканирования для Dockerfile указано
**0 ошибок конфигурации**. Обе первоначальные сработки устранены.
Этот результат относится к конфигурации Dockerfile и не отменяет
находки зависимостей в отчёте сканирования образа.
