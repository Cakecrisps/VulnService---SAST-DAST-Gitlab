ТЗ на простой уязвимый сервис заметок
Цель: собрать небольшой учебный сервис для последующей практики сканирования и поиска уязвимостей. Сейчас делаем только уязвимую версию.
1. Что запускаем
Два контейнера через Docker Compose:
- app — Python + FastAPI, API и Swagger /docs.
- db — PostgreSQL с пользователями и заметками.
Приложение доступно на 127.0.0.1:8000. PostgreSQL доступен приложению по db:5432, без публикации порта на хост. Данные БД хранятся в volume. Фронтенд не нужен.
2. Данные
Две таблицы:
- users: id, username, password.
- notes: id, user_id, title, body.
При первом запуске автоматически создать таблицы и два учебных аккаунта: alice / alice и bob / bob. У каждого — по две заметки с вымышленным содержимым. Повторный запуск не должен дублировать записи.
Для простоты пароли хранятся открытым текстом. Это отдельное намеренное учебное упрощение, не пример правильного хранения паролей. Только тестовые учётные данные.
3. Простой вход
POST /login принимает JSON с username и password.
При верных данных приложение создаёт случайный непрозрачный токен, сохраняет соответствие «токен → user_id» в обычном словаре Python и возвращает токен. При неверных — 401. Проверку логина выполнить параметризованным запросом.
Все запросы к заметкам принимают Authorization: Bearer <token>. Неизвестный или отсутствующий токен — 401. После перезапуска приложения нужно войти заново. Один процесс Uvicorn, без нескольких workers.
JWT, срок жизни токенов, регистрацию, роли и требования к сложности паролей не реализовывать.
4. API
Метод и адрес	Что делает
POST /login	Вход и получение токена
GET /notes	Список заметок текущего пользователя
POST /notes	Создание заметки: JSON с title и body; user_id берётся из токена
GET /notes/search?q=текст	Поиск по заголовкам своих заметок; намеренная SQL-инъекция
GET /notes/{id}	Получение заметки по ID; намеренная ошибка доступа


Возвращать JSON. Если заметки нет — 404, если поиск ничего не нашёл — пустой список. Для создания достаточно непустого строкового title и строкового body, без сложных ограничений. Маршрут /notes/search объявить раньше /notes/{id}.
Редактирование, удаление, пагинация и отдельные health endpoints не нужны.
5. Две целевые уязвимости
SQL injection в поиске. Значение q подставляется прямо в текст SQL через форматирование строки. При обычном запросе поиск ограничен заметками текущего пользователя, но специально сформированный ввод позволяет изменить условие запроса. Остальные запросы к БД сделать параметризованными, чтобы место этой уязвимости было однозначным.
IDOR в получении заметки. /notes/{id} требует входа, но выбирает запись только по ID, без проверки user_id. Поэтому Bob, зная ID заметки Alice, получает её содержимое. При этом /notes штатно показывает только собственные заметки.
Обе уязвимости должны оставаться в готовой версии этого этапа. Помимо них предусмотрено открытое хранение учебных паролей, описанное выше.
6. Что должно лежать в проекте
- Код приложения: достаточно нескольких Python-файлов, допускается один main.py.
- requirements.txt.
- Dockerfile для приложения.
- compose.yaml с app и db.
- Инициализация таблиц и тестовых данных — любым простым способом.
- Короткий README.md: запуск, учебные аккаунты, примеры запросов и места двух уязвимостей.
Для доступа к БД достаточно psycopg и обычного SQL. ORM, миграции, CI/CD, сканеры, автотесты и исправленная версия пока не требуются. Учебные настройки БД можно указать прямо в Compose; реальные секреты не использовать.
7. Когда готово
1. docker compose up --build запускает два контейнера; приложение дожидается готовности БД любым простым способом.
2. /docs открывается, Alice и Bob могут войти.
3. Пользователь создаёт заметку и видит её в своём списке.
4. Обычный поиск работает.
5. Bob может прочитать заметку Alice по ID — IDOR воспроизводится.
6. На тестовых данных можно показать изменение результата поиска через SQL injection.
7. После перезапуска контейнеров заметки сохраняются.
Стенд работает только локально и содержит вымышленные данные. На этом этапе этого достаточно.
