# Отчёт о динамическом анализе (DAST)

## Стенд и отчёты

Я проверил работающий учебный сервис заметок с помощью ZAP 2.17.0.
Цель сканирования — `http://127.0.0.1:8000`, дата — 30 сентября 2026 года.

В папке `reports` сохранены два набора результатов:

| Проверка | HTML-отчёт | JSON-отчёт | Время создания, UTC |
| --- | --- | --- | --- |
| Без авторизации | [zap-report.html](reports/zap-report.html) | [zap-report.json](reports/zap-report.json) | 20:01:30 |
| С авторизацией | [zap-auth-report.html](reports/zap-auth-report.html) | [zap-auth-report.json](reports/zap-auth-report.json) | 20:08:53 |

При первом сканировании защищённые маршруты заметок возвращали `401`.
В этом отчёте SQL-инъекция не обнаружена. При повторной проверке с
авторизацией ZAP смог обратиться к поиску и зарегистрировал SQL Injection.

## SQL-инъекция в поиске заметок

В отчёте с авторизацией я получил следующую сработку:

| Поле | Значение |
| --- | --- |
| Название | SQL Injection |
| Правило ZAP | `40018` |
| Классификация | CWE-89, WASC-19 |
| Уровень риска | High |
| Уверенность сканера | Low |
| Метод и маршрут | `GET /notes/search` |
| Параметр | `q` |
| Тестовый ввод | Одиночная кавычка: `'` |
| URL из отчёта | `http://127.0.0.1:8000/notes/search?q=%27` |
| Свидетельство в отчёте | `HTTP/1.1 500 Internal Server Error` |
| Количество зарегистрированных экземпляров | 1 |

ZAP передал кавычку в параметре поиска и получил внутреннюю ошибку сервера.
Я сопоставил сработку с кодом [main.py](main.py): функция `search_notes`
вставляет `q` непосредственно в SQL через f-строку, а затем передаёт
получившийся запрос в `conn.execute(query)`.

```python
q = lab_sanitize(q)
query = (
    "SELECT id, user_id, title, body FROM notes "
    f"WHERE user_id = {user_id} AND title ILIKE '%{q}%' ORDER BY id"
)
```

Функция `lab_sanitize` возвращает входную строку без изменений, поэтому
её вызов не устраняет SQL-инъекцию. Кавычка нарушает структуру SQL-запроса,
что согласуется с ошибкой, зафиксированной сканером.

Сам по себе HTTP 500 не доказывает успешную эксплуатацию: ZAP обозначил
уверенность как Low. Наличие уязвимости я также подтвердил ранее при
ручной проверке стенда. Ввод `' OR TRUE -- ` меняет условие поиска и
позволяет получить заметки других пользователей. Этот пример ручной
проверки не является payload из отчёта ZAP: в отчёте сохранена одиночная
кавычка.

Причина уязвимости — смешивание пользовательских данных и текста SQL.
Для исправления потребовалось бы передавать поисковую строку параметром
запроса. На этом этапе я оставил SQL-инъекцию в сервисе намеренно,
поскольку она предусмотрена заданием для учебного стенда.

## Остальные результаты

Ниже я свёл количество типов предупреждений по уровню риска.
Это число записей `alerts`, а не число запросов или всех экземпляров находок.

| Проверка | High | Medium | Low | Informational |
| --- | --- | --- | --- | --- |
| Без авторизации | 0 | 0 | 2 | 4 |
| С авторизацией | 1 | 0 | 3 | 3 |

Помимо SQL-инъекции, в отчёте с авторизацией зарегистрированы:

| Предупреждение | Уровень риска | Экземпляров |
| --- | --- | --- |
| A Server Error response code was returned by the server | Low | 2 |
| Cross-Origin-Resource-Policy Header Missing or Invalid | Low | 4 |
| X-Content-Type-Options Header Missing | Low | 4 |
| A Client Error response code was returned by the server | Informational | 18 |
| Authentication Request Identified | Informational | 1 |
| Non-Storable Content | Informational | 5 |

Информационные записи о входе, кешировании и кодах ответа не считаю
автоматически подтверждёнными уязвимостями. Например, `401` при отсутствии
действительного токена и `404` для несуществующего маршрута соответствуют
поведению сервиса.

Отдельной сработки BOLA/IDOR в этих отчётах ZAP нет. Ошибку доступа к чужой
заметке через `GET /notes/{id}` я подтвердил вручную ранее; отсутствие
предупреждения в автоматическом отчёте не означает её устранения.
